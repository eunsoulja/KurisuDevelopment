================================================================================
1. WHAT THE BOT IS
================================================================================

Kurisu is a Discord antinuke, raid-protection and moderation bot.

Main areas:
  - Antinuke with 28 configurable modules.
  - Nuke Guard: cross-module destructive-burst detection.
  - 24-hour nuke watch: a kicked nuke executor is banned on sight.
  - Raid protection with levels, lockdown, verification mode and join history.
  - Whitelist for users AND roles, with per-module scopes.
  - Moderation commands and case/warning history.
  - Recovery: restore channels/roles, remove webhooks/bots/invites, revert danger.
  - Security Center (/security) and Command Center (/help), both Components V2.
  - Bot-network overview (/guilds), bot-owner only.
  - Prefix text commands using the same permission and V2 response pipeline.

Current scale:
  - 38 top-level slash commands.
  - 24 subcommands.
  - 53 help entries (top-level commands + subcommands).
  - 28 antinuke modules.
  - 38 automated tests, all passing.

3. THEME AND UI RULES - STRICT
================================================================================

Kurisu uses Discord Components V2, not classic embeds.

Hard rules:
  - No EmbedBuilder.
  - No embed colors, accent colors, side bars or brand-color strips.
  - No ButtonStyle.Primary, Success or Danger.
  - All buttons must be grey/secondary, created through ui.btn() or ui.emojiBtn().
  - The only color in the UI is the red custom emoji set.
  - Use the emoji registry in src/config/emojis.js through E / ui.E.
  - Do not invent emoji IDs. Do not use unrelated colored emojis.
  - Use the shared helpers in src/components/common/ui.js:
        ui.text / ui.sep / ui.btn / ui.emojiBtn / ui.buttons / ui.select
        ui.userSelect / ui.roleSelect / ui.channelSelect
        ui.container / ui.message / ui.edit / ui.notice / ui.error / ui.respond
  - Use ui.message() for replies and ui.edit() for updates.
  - Ephemeral for personal/sensitive views; public only for shared panels.
  - Re-authorize every component interaction. Do not trust the customId.

Current visual language:
  - Header:        ### <emoji> TITLE
  - Subheader:     -# short subtitle
  - Divider:       'sep'
  - Spacing only:  'sep:blank'
  - Label/value:   Label  **Value**
  - Group headings with bold text, then separated blocks.
  - Relative timestamps: <t:UNIX:R>
  - Compact footers with -#.
  - Section rows may use a thumbnail or a single button accessory.

Current clean-layout patterns (keep these):
  - Security Center main: status block, overview, nuke guard, last incident.
  - Protection Modules: 10 modules per page, one select for that page, page nav.
  - Settings: Protection, Escalation/Prefix, Log Channels.
  - Raid: Status, Join Thresholds, Accounts; config row then action row.
  - Logs/Incidents: action on line 1, metadata on line 2.
  - Whitelist: Grant level, Scope, Add or update, Remove.
  - /guilds: network totals, per-server lines, grey pagination + Refresh.

Important wording: the user says "embed" colloquially. Kurisu cards are
Components V2 containers. Do not switch them to classic Discord embeds.

  Remove a trusted user or role.

  List trusted users and roles.

  Check a user's exemption status.
  Permission: Server Owner or Trusted Administrator.

  Whitelist levels:
    trusted_admin  Trusted Administrator
    trusted_mod    Trusted Moderator
    bypass         Security Bypass
    bot            Trusted Bot

  Authority:
    - Guild owner and bot owners can grant any level.
    - Trusted Administrators may only grant trusted_mod and bot.
    - Owner protections cannot be removed.
    - Administrator permission alone gives no antinuke immunity and no
      whitelist authority. A Trusted Administrator must also have a whitelist
      entry with the trusted_admin level.

    default, all, pings, mentions, channels, channel-create, channel-rename,
    channel-delete, roles, members, webhooks, server, invites, messages,
    emojis, assets, threads, automod, bots, permissions, nuke

  If scopes are omitted:
    - trusted_mod bypasses message modules only (legacy default).
    - trusted_admin, bypass and bot are fully exempt.
  Scoped entries only bypass the listed modules. '*' means all modules.

5. SECURITY MODEL / ANTINUKE
================================================================================

Actors:
  - Guild owner: always exempt; cannot be punished.
  - Bot owners (OWNER_IDS): always exempt; cannot be punished.
  - Kurisu itself: always exempt.
  - Whitelist users/roles: exempt according to level and scopes.
  - Administrator permission alone: NOT exempt.

Punishments:
  strip, quarantine, timeout, kick, ban

Escalation:
  Default 2 incidents in 24 hours -> escalate to ban.
  Configurable; 0 disables escalation.

28 antinuke modules:
  channelCreate, channelDelete, channelUpdate,
  roleCreate, roleDelete, roleUpdate,
  massBan, massKick, massUnban, prune,
  webhookCreate, webhookDelete, webhookUpdate,
  botAdd, guildUpdate,
  everyoneMention, massMention,
  permEscalation, integration, inviteSpam, massDelete,
  emojiDelete, stickerDelete, threadDelete, assetCreate,
  automodRule, vanityChange, nukeGuard

Critical defaults (faster kicks):
  channelDelete    2 actions / 10s  -> kick
  roleDelete       2 actions / 10s  -> kick
  botAdd           1 action  / 60s  -> kick
  permEscalation   1 action  / 60s  -> kick
  automodRule      1 action  / 30s  -> kick
  vanityChange     1 action  / 60s  -> kick
  prune            1 action  / 60s  -> kick
  massBan          3 actions / 15s  -> ban
  massKick         3 actions / 15s  -> ban
  massUnban        3 actions / 15s  -> kick
  nukeGuard        3 actions / 10s  -> kick

Nuke Guard:
  - Runs before per-module thresholds.
  - Counts destructive actions across all enabled "nuke" modules per executor.
  - At 3 destructive actions in 10 seconds (default), it kicks immediately.
  - This stops mixed attacks (channel delete + role delete + ban wave) that
    might otherwise stay under each individual threshold.
  - A kicked nuke executor is added to the persistent 24-hour nuke watch.
  - Any auditable action, message or rejoin while watched results in a ban.
  - The watch survives restarts because it is stored in the nuke_watch table.
  - The recent cross-module burst window is mirrored in nuke_recent, so a
    burst split across a restart is still caught.
  - Incidents label every module key involved in a mixed burst, not just the
    first one.

Early alert:
  - The first hit on a destructive module, while still below threshold,
    writes a "Security Watch" line to the antinuke log.

Detection pipeline:
  - Source: GUILD_AUDIT_LOG_ENTRY_CREATE.
  - Duplicate audit entry IDs are dropped.
  - Entries with no executor are ignored; Kurisu never punishes an arbitrary
    member.
  - Entry is mapped to one or more modules.
  - Owner-class, Kurisu and whitelisted actors are skipped.
  - Nuke Guard is evaluated first.
  - Then the per-module sliding window and per-executor lock.
  - Punishment is applied with a fallback chain if Discord refuses.
  - Affected objects are mitigated (restore, revert or remove).
  - An incident row and a log line are written.

Whitelist specifics:
  - Trusted Administrator requires Administrator permission PLUS a
    trusted_admin whitelist entry.
  - Role whitelist entries are supported.
  - Scoped entries only bypass listed modules.
  - Owner protections cannot be removed.
  - Trusted Administrators can only grant trusted_mod and bot levels.
  - Disabling antinuke or raid protection requires server owner or bot owner.
  - /massban and /masskick require a whitelist exemption for their module.

Raid protection:
  - Levels: NORMAL, ELEVATED, HIGH, LOCKDOWN.
  - Defaults: 5 joins = ELEVATED, 10 = HIGH, 20 = LOCKDOWN in a 10s window.
  - New-account age default: 7 days.
  - Auto lockdown default: on, 15 minutes.
  - Kick suspicious accounts during lockdown: off by default.
  - HIGH raises Discord verification level.
  - LOCKDOWN sets Very High verification, blocks @everyone send permissions,
    and pauses invites.
  - Raid protection never mass-bans. Optional lockdown kicks only remove
    accounts younger than the configured minimum age.
  - Lockdown state and channel state are stored in SQLite; expired lockdowns
    are resolved on startup.

Recovery:
  - Snapshots of channels/roles/settings.
  - Restore channels and roles (new Discord IDs).
  - Revert role/channel/server-name changes.
  - Remove webhooks, unapproved bots and invites.
  - Restored overwrites never regain dangerous permissions.

Discord API limits:
  - Messages in a deleted channel cannot be recovered.
  - Restored channels/roles get new IDs.
  - Members of a deleted role are not re-assigned.
  - Server icon, banner and vanity URL cannot be restored.
  - Bulk message deletion is detected through audit entries, not a perfect
    per-message count.
  - Quarantine uses removed roles, a permissionless role and a 28-day timeout
    because Discord caps timeouts.
  - Message logs intentionally omit message content.

  - guild config, antinuke module config, raid config
  - whitelist, warnings, moderation cases, incidents
  - log channels, snapshots, quarantine, join history
  - lockdown state and nuke watch
  - the recent cross-module actions used by Nuke Guard (2-minute prune;
    the guard window itself is shorter, default 10 seconds)

In-memory only (resets on restart):
  - antinuke sliding windows
  - audit-entry dedupe cache
  - per-executor punishment locks
  - early-watch alert dedupe

Back up the data/ directory before major changes.
Do not commit data/kurisu.db.

MongoDB target notes:
  - Atlas database name from the current URI: prismo.
  - Keep Discord snowflakes as strings.
  - Keep timestamps as epoch milliseconds for drop-in compatibility.
  - Preserve numeric case/incident/warning IDs with a counters collection.
  - MongoDB TTL indexes only expire BSON Date values, not numeric epoch values.
    Keep the numeric expires_at for compatibility and add a BSON Date field
    (for example expires_at_date) for the TTL index, or convert expires_at to
    a Date and adapt the repo. Still filter expired rows in code because the
    TTL monitor is not immediate.
  - Full collection mapping, indexes and rollout steps: section 9.0.

--------------------------------------------------------------------------------
9.0 MONGODB MIGRATION (PLANNED - P0 BACKEND CHANGE)
--------------------------------------------------------------------------------

Decision: replace SQLite/better-sqlite3 with MongoDB Atlas.
  - Connection string: DATABASE_URL in .env.
  - Atlas database name in the provided URI: prismo.
  - Never hardcode the URI or commit it. It contains a username and password.
  - If a URI with a real password has been shared in chat or logs, rotate that
    database user's password before production use.

This is not a drop-in driver swap. The current repository layer is synchronous
(better-sqlite3), while every MongoDB driver operation is asynchronous. Expect
a large refactor and treat it as a breaking backend change (version 2.0.0).

Phase 1 - preparation
  - Back up the whole data/ folder, especially data/kurisu.db.

Phase 2 - rewrite the database layer
  - src/database/index.js:
      * MongoClient connect/close, database selection, startup ping.
      * ensureIndexes() instead of SQL migrations.
      * Connection failure must produce a clear fatal startup message.
      * Do not log the URI; it contains credentials.
  - src/database/repo.js:
      * Convert every function from synchronous to async.
      * Replace prepared statements with findOne, find, insertOne, updateOne,
        findOneAndUpdate, countDocuments and aggregate.
      * Use upserts plus unique indexes for settings/config/watch entries.
      * Add a `counters` collection for numeric IDs. Cases, incidents, warnings,
        recovery_log and join_history currently rely on integer IDs; preserve
        them with an atomic nextId(name) helper.
  - Update every caller:
      * src/commands/**, src/components/**, src/engines/**, src/events/**.
      * Search for `repo.` and add `await` where needed. A missed await returns
        a Promise instead of data and will silently break logic.
  - src/index.js:
      * `await db.open()` before client.login().
      * Close the Mongo client on SIGINT/SIGTERM.
  - Cache hot reads (prefix, module config, whitelist) where appropriate so a
    Mongo round-trip is not added to every message event.

Collection mapping (SQLite -> MongoDB):
  guild_settings      -> guild_settings      _id = guild_id
  antinuke_modules    -> antinuke_modules    unique {guild_id, module}
  raid_config         -> raid_config         _id = guild_id
  lockdown_channels   -> lockdown_channels   unique {guild_id, channel_id}
  whitelist           -> whitelist           unique {guild_id, user_id};
                                              keep target_type and scopes
  warnings            -> warnings            id + guild_id + user_id + ...
  mod_cases           -> mod_cases           id + guild_id + user_id + ...
  incidents           -> incidents           id + guild_id + executor_id + ...
  log_channels        -> log_channels        unique {guild_id, type}
  snapshots           -> snapshots           unique {guild_id, kind, target_id}
  recovery_log        -> recovery_log        id + guild_id + ...
  quarantine          -> quarantine          unique {guild_id, user_id}
  join_history        -> join_history        id + guild_id + joined_at + ...
  nuke_watch          -> nuke_watch          unique {guild_id, user_id};
                                              TTL on expires_at_date (BSON
                                              Date); keep numeric expires_at
                                              for repo compatibility
  nuke_recent         -> nuke_recent         unique {guild_id, executor_id,
                                              entry_id}; TTL on created_at_date
                                              or prune in code

Recommended indexes:
  antinuke_modules  { guild_id: 1, module: 1 } unique
  whitelist         { guild_id: 1, user_id: 1 } unique
  log_channels      { guild_id: 1, type: 1 } unique
  snapshots         { guild_id: 1, kind: 1, target_id: 1 } unique
  quarantine        { guild_id: 1, user_id: 1 } unique
  nuke_watch        { guild_id: 1, user_id: 1 } unique
  nuke_watch        { expires_at_date: 1 } TTL, expireAfterSeconds: 0
                    (must be a BSON Date, not epoch milliseconds)
  nuke_recent       { guild_id: 1, executor_id: 1, created_at: -1 }
  nuke_recent       { guild_id: 1, executor_id: 1, entry_id: 1 } unique
  mod_cases         { guild_id: 1, user_id: 1, created_at: -1 }
  mod_cases         { guild_id: 1, id: 1 } unique
  incidents         { guild_id: 1, created_at: -1 }
  incidents         { guild_id: 1, executor_id: 1, created_at: -1 }
  incidents         { guild_id: 1, id: 1 } unique
  warnings          { guild_id: 1, user_id: 1, created_at: -1 }
  join_history      { guild_id: 1, joined_at: -1 }
  recovery_log      { guild_id: 1, created_at: -1 }
  lockdown_channels { guild_id: 1, channel_id: 1 } unique

  - Clear collections between tests and preserve the guild-isolation test.
  - Keep node --test tests/kurisu.test.js as the entry point.

Phase 5 - cleanup and rollout
  - Remove better-sqlite3 and SQLite-specific code only after validation.

Main risks:
  - Missed `await` during the sync-to-async refactor.
  - Numeric IDs changing or colliding; use counters, not ObjectId display.
  - Atlas IP allowlist/SRV/network failures blocking startup.
  - Added latency on hot paths if caches are removed.
  - Race conditions on upserts; rely on unique indexes and atomic operators.
  - Credential leakage through logs, errors or committed files.

Acceptance criteria:
  - Bot starts only after a successful Mongo connection and index setup.
  - All tests pass against an isolated test database.
  - Existing SQLite data is migrated with matching counts and IDs.
  - Config, whitelist, cases, incidents, warnings, snapshots, nuke watch and
    the Nuke Guard recent-burst window survive a bot restart.
  - /security, /guilds and the antinuke pipeline work unchanged from the user's
    perspective.

  - Do not assume "k" is the default prefix.
  - Do not commit .env, tokens, the SQLite database, the MongoDB URI or the zip.
  - Do not paste the Atlas URI into source, logs, README, bot.txt or commits.
  - Do not start the MongoDB migration without a SQLite backup and a rollback.
  - Do not convert repo methods halfway; the sync-to-async change must be
    complete or the whole bot will misbehave.
  - Do not run destructive tests on a real community. Use a disposable guild.
  - Do not add a new emoji unless it exists in the registry and the bot can
    see it as a guild emoji or application emoji.
  - Keep slash commands and text commands working for every top-level command.
  - Keep the UI helper patterns; do not hand-build inconsistent containers.
  - If a command name or option changes, redeploy slash commands.
  - If a public view changes, keep customIds backward compatible where
    practical, or make old messages fail gracefully.
